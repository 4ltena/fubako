# 企画書：文箱（ふばこ）

作成日：2026年9月2日
版：0.1（ブレスト直後の初版）

---

## 一行で

推し活の話を、地雷を踏む心配なしに雑に投げられる小さな場。読み手が「見たくないもの」を宣言しておくと、システムが自動で伏せる。

仮称の「ふばこ」は、囲われた狭い場という意味と、地雷を囲って伏せるという意味を掛けている。名前は差し替え可能。

---

## 1. 何が困りごとなのか

ブレストの最終地点は「安心して雑に投げられない」だった。この一文には、性質の違う3つの要求が入っている。

- **安心して** — 投げたあとの帰結を自分で制御できない
- **雑に** — 投げる前の準備コストが高い
- **投げる** — 受け手がいる（メモ帳ではない）

ボードに出た課題の付箋10枚のうち、9枚が「安心して」に集中していた。案の付箋9枚も全部そちら向けだった。

だが安心は、鍵垢とDiscordの個人サーバーで既に達成されている。空いているのは残り2つのほうである。

とくに「雑に」は、快適さの問題ではない。推し活の感情は鮮度が短い。配信中の「今のよかった」は、体裁を整えている間に価値が落ちる。準備時間が感情の寿命を超えると、投稿そのものが起きない。雑さは、投稿が成立するかどうかの条件になっている。

---

## 2. 今ある手段で足りない理由

競合は他のSNSではない。**ユーザーが自分で組んだ運用**が競合である。

鍵垢、サブ垢、Discordの個人サーバー、自分だけのLINEグループ。どれも安心と雑さは満たしている。足りないのは、その安心を毎回自分の手で作らなければならない点だ。

地雷回避の現状は「自衛してください」である。書く側は注意書きを手で付け、読む側はミュートワードを手で登録する。両方が手作業で、しかも噛み合っていない。ふせったーは書く側だけを機械化した。読む側は手つかずのまま残っている。

この領域で生き残ったサービス（ふせったー、Privatter、ポイピク、マシュマロ）は、どれも新しい体験を発明していない。それまで手でやられていた作法を機能にしただけである。この企画も同じ系譜に置く。

したがって乗り換え理由は「できないことができる」ではなく、**「自衛の手間が減る」**になる。

---

## 3. 何を作るか

背骨は一つ。**読み手側の自衛を機械化する。**

### 機能（v1）

**サークル**
招待コードで入る小さな場。人数に上限を置く（初期値30人）。検索で見つからない。参加していない人からは存在自体が見えない。

**投稿**
テキスト中心。投稿時に寿命を選ぶが、既定値を持たせて無選択でも投稿できる。

**地雷宣言**
読み手が「見たくない語」を登録する。一致した投稿は本文を伏せた状態で流れてくる。伏せた理由（一致した語）は表示する。読み手が自分でタップすれば開く。ふせったーの読み手版にあたる。

**未タグは既定で伏せる**
書き手にタグ付けを強制しない。ただしタグのない投稿は、地雷宣言をしている読み手には「未確認」として伏せられる。これで2つが同時に片づく。タグ付けの動機が生まれること、そして判定漏れが安全側に倒れることである。

**反応**
1種類だけ。数は誰にも見えない（投稿者にも）。返信欄は作らない。

**通知**
プッシュを持たない。1日1回、決まった時刻にダイジェストを出すだけ。押し出さず、来たときに渡す。

**可視性の時間非対称**
投稿は寿命を過ぎると他のメンバーから見えなくなるが、書いた本人のアーカイブには残る。デジタルタトゥーも誤爆も「他人が持っていること」が問題なので、自分側に残っても安心は壊れない。

### 作らないもの

DM、フォロー、検索、公開プロフィール、引用、返信欄、いいね数の表示、プッシュ通知。

全部が静かさを壊す。ここは意志を持って空欄にする。

---

## 4. 設計原則

ブレストで出た案のうち3つ（届く上限を投稿者が決める／投稿後に範囲を変更する／投稿時に寿命を選ぶ）は、安心を上げる代わりに投稿前後の判断を増やしていた。安心を「ユーザーに選ばせる」形で実装すると、雑さが死ぬ。

そこで3つの原則を置く。実装で迷ったらここに戻る。

**A. 選ばせない**
範囲も寿命も既定値を持つ。設定画面を増やさない。

**B. 事後に取り消せる**
判断を後ろにずらす。投げるのは無条件、消すのは後からできる。寿命は短くする方向にだけ変更できる（長くはできない）。

**C. 数えない・急かさない**
反応は届くが、数と催促は持たない。

---

## 5. 差別化と、正直な弱み

### 差別化

読み手側の自衛を機械化した製品は、たぶんまだない。そして一般プラットフォームは作らない。一般ユーザーに需要がないからである。ニッチさは弱点ではなく、参入されない理由になる。

### 弱み1：タグ付けは書き手の負担になる

これは企画の核（雑に投げられる）と正面から衝突している。読み手のコストを書き手に移しているだけ、とも言える。

v1では強制しない。未タグを伏せることで動機だけ作る。Phase 2で本文からのタグ自動推定を入れて、書き手は確認するだけにする。この製品でLLMが必然的に効く場所は、おそらくここ一箇所だけである。

### 弱み2：判定漏れのコストが非対称

1回漏れたら信頼が終わる。だから約束の言葉を「自衛しなくていい」ではなく「自衛の手間が減る」に弱める。伏せは自動と手動の二重にし、漏れを報告する導線を最初から置く。

### 弱み3：静かな場は死んだ前例がある

Pathは家族と親しい友人に絞ったクローズドSNSで、繋がれる人数を50人（のちに150人）に制限していた。2010年に始まり、2018年10月18日にアクセスを停止、11月15日に完全終了している。SNS疲れの受け皿として支持されたが、8年で畳まれた。

静かさそのものは売りにならない、と読むべきだと考えている。売りは地雷回避のほうに置く。

### 弱み4：地雷の語彙は速く変わる

界隈ごとに違い、しかも入れ替わる。固定のタグ体系を作ると破綻する。だからタグは自由入力にして、そのサークル内でよく使われた語をサジェストする形にする。

### 弱み5：機械化すると壊れる作法がある

手で注意書きを書く行為は、配慮の表明でもある。自動化すると配慮が見えなくなり、「この人は気を遣ってくれる人だ」という判断材料が消える。作法が持っていた社交的な機能まで奪わないか、運用しながら見る必要がある。

---

## 6. 作る前に確かめること（1〜2週間）

危険な仮説がひとつある。**反応が薄い場所に、人は投稿し続けるか。**

- 鍵垢と定期削除の組み合わせで、まず自分が1〜2週間運用する。書き続けられるか
- 推し活をしている5〜10人に、いまの鍵垢の使われ方を聞く。何が不満で、何が満足か
- 質問は「こういうサービスがあったら使いますか」ではなく「いまの鍵垢をやめてこちらに移りますか」にする。前者は全員がイエスと言う

最優先で確かめたいのはひとつだけ。**タグを付ける行為は、実際に負担と感じられているか。** 既に習慣化していて負担でないなら、弱み1が消えて設計が軽くなる。逆に強い負担なら、Phase 2の自動推定を前倒しする必要がある。

---

## 7. 指標

- **成功**：導入した人が2週間後も週2回以上投稿している
- **撤退**：初週で投稿が止まる人が半数を超える。または「結局Xに書いた」が多数

数ではなく継続を見る。バズは指標にしない。この製品は、バズが起きたら設計が失敗している。

---

## 8. 技術構成

**Webアプリ1本で作る。Androidネイティブにはしない。**

理由は、この製品がプッシュ通知を持たない設計だからである。ネイティブアプリの最大の利点が、設計上そもそも要らない。カメラもセンサも位置情報も使わない。個人開発で一本に絞れるほうが速い。

PWAにすればAndroid 12以降のChromeからホーム画面に追加できる。もしアプリとしての配布が要件になるなら、BubblewrapでTWAとして包めばPlay Storeにも出せる。そのときも中身はこのWebアプリのままでよい。

| 層 | 採用 |
|---|---|
| フロント / サーバ | Next.js (App Router) + TypeScript + Tailwind CSS |
| DB | PostgreSQL + Prisma |
| 認証 | Auth.js（Discord OAuth ＋ メールのマジックリンク） |
| タグ自動推定（Phase 2） | Anthropic API をサーバ側から呼ぶ |
| ダイジェスト | cron で1日1回 |
| ホスティング | Vercel + Neon |

X APIは使わない。相互フォローのグラフを取るには有料枠が必要になる可能性が高く、個人開発の前提が崩れる。狭さは招待コードと人数上限で作る。

検索避けは実装で担保する。robots.txtで全面Disallow、全ページnoindex、OGPを出さない。伏せた投稿の本文はサーバ側で落とす（クライアントでCSS的に隠すのではなく、APIのレスポンスに含めない）。

---

## 9. 進め方

| 段階 | 内容 |
|---|---|
| 0 | ヒアリング5〜10人。鍵垢の使われ方とタグ付けの負担を聞く |
| 1 | サークル、投稿、タイムライン。伏せ機能なし |
| 2 | 地雷宣言と伏せ。ここまでで一度使ってもらう |
| 3 | 反応、アーカイブ、寿命、ダイジェスト |
| 4 | PWA化、検索避け、招待の運用 |
| 5 | タグの自動推定（Anthropic API） |

段階2で一度止めて人に触ってもらう。ここで「伏せが役に立った」という反応が出なければ、背骨が間違っている。

---

## 10. まだ決めていないこと

1. **投げる相手は誰か。** 同担の他人か、特定の友人か、未来の自分か。ここで別プロダクトになる
2. **名前。** 「ふばこ」は仮
3. **サークルの人数上限。** 初期値30人としたが根拠は弱い。Pathの50人が参考になる
4. **寿命の既定値。** 7日を想定しているが未検証
5. **画像を許すか。** 推し活の投稿はグッズ写真やスクショが中心なので落とすと痛い。ただし身バレと転載のリスクが上がり、タグの自動推定も難しくなる

---

## 補足：この企画書の弱いところ

ここに書いたことの大半は、ブレストボードの情報から論理で組み立てたものである。実際の界隈の運用は見ていない。とくに「タグ付けは負担である」という前提が崩れると、弱み1の議論が丸ごと不要になる。段階0のヒアリングは、体裁ではなく本当に必要な工程として置いている。
